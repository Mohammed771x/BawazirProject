# الوثيقة رقم 5 — معمارية النظام (System Architecture)

## 1. الهدف من المعمارية

تم تصميم معمارية **WordOS** بحيث تحقق ثلاثة أهداف رئيسية في الوقت نفسه:

1. **فصل المسؤوليات بوضوح** بين واجهة التطبيق، منطق النظام، الذكاء الاصطناعي، وقاعدة البيانات.
2. **الحفاظ على الخوارزمية الأساسية تحت سيطرة النظام** وعدم جعلها معتمدة بشكل مباشر على نموذج ذكاء اصطناعي معين.
3. **إتاحة التوسع مستقبلًا** دون الحاجة إلى إعادة بناء التطبيق من الصفر.

WordOS ليس مجرد تطبيق يعرض كلمات للمستخدم، وإنما نظام يدير دورة حياة الكلمة من لحظة إضافتها، مرورًا بالمهارات الخمس، وحتى استخدامها داخل Active Vocabulary ثم أرشفتها.

لذلك يجب أن تكون الـ Architecture قادرة على التعامل مع:

* المستخدمين.
* الكلمات.
* مستويات المستخدم.
* مستويات المهارات المختلفة.
* Learning Pipeline.
* ترتيب الكلمات وأولوياتها.
* المهارات الخمس.
* المحتوى المولد بواسطة AI.
* تقييم إجابات المستخدم.
* المراجعات الأسبوعية.
* إعدادات المستخدم.
* الـ Logging والـ Analytics.
* ومراقبة أداء الخوارزمية.

# 2. المعمارية العامة

يعتمد WordOS في الـ MVP على **Layered / Modular Architecture** بدلًا من بناء Microservices متعددة منذ البداية.

الشكل العام للنظام:

```text
                 ┌──────────────────────┐
                 │      Flutter App     │
                 │    Mobile Frontend   │
                 └──────────┬───────────┘
                            │
                       RESTful API
                            │
                            ▼
                 ┌──────────────────────┐
                 │    ASP.NET Core API  │
                 │      C# Backend      │
                 └──────────┬───────────┘
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
   ┌─────────────┐   ┌──────────────┐  ┌──────────────┐
   │ Business    │   │ WordOS       │  │ Analytics &  │
   │ Logic       │   │ Algorithm    │  │ Logging      │
   └─────────────┘   └──────────────┘  └──────────────┘
          │                 │
          └────────┬────────┘
                   │
                   ▼
          ┌──────────────────┐
          │    PostgreSQL    │
          │     Database     │
          └──────────────────┘

                   ▲
                   │ RESTful API
                   ▼

          ┌──────────────────┐
          │   Python AI      │
          │     Service      │
          └────────┬─────────┘
                   │
                   ▼
          ┌──────────────────┐
          │    AI Provider   │
          │    / AI APIs     │
          └──────────────────┘
```

هذه المعمارية تعني أن **Flutter لا يتعامل مباشرة مع قاعدة البيانات أو AI APIs**.

كما أن الـ AI لا يمتلك القرار النهائي حول حالة الكلمة داخل النظام.

الـ Backend هو المسؤول عن ذلك.

# 3. Flutter Mobile Application

## 3.1 المسؤولية

Flutter هو الـ **Frontend** الخاص بتطبيق WordOS على الهاتف.

وظيفته الأساسية هي:

* عرض واجهات التطبيق.
* استقبال إدخال المستخدم.
* عرض الكلمات والمحتوى.
* تشغيل الصوت.
* تسجيل صوت المستخدم عند الحاجة.
* عرض الأسئلة.
* إرسال إجابات المستخدم إلى Backend.
* استقبال النتائج وعرضها.
* إدارة تجربة المستخدم UI/UX.

Flutter **لا يحتوي على Business Logic الأساسية للخوارزمية**.

بمعنى أن Flutter لا يقرر:

> هل الكلمة انتقلت من Reading إلى Listening؟

ولا يقرر:

> هل الكلمة أصبحت Mature؟

ولا يقرر:

> هل يجب أرشفة الكلمة؟

هذه القرارات يجب أن تأتي من Backend.

# 6. لماذا يكون الـ Business Logic في C#؟

الهدف هو أن تكون القواعد الأساسية للنظام مستقلة عن الذكاء الاصطناعي.

مثلًا:

```text
إذا نجحت Reading
        ↓
انتظر الفترة المحددة
        ↓
افتح Listening
```

هذا **ليس قرار AI**.

وكذلك:

```text
Reading ✓
Listening ✓
Writing ✓
Speaking ✓
Spelling ✓
        ↓
Mature
```

هذا قرار من WordOS Algorithm.

والـ Backend هو المسؤول عن تنفيذ هذه القواعد.

وبذلك إذا تم تغيير AI Provider مستقبلًا، لن نحتاج إلى إعادة بناء الخوارزمية.

# 9. مبدأ Persistence

من أهم متطلبات WordOS أن البيانات **لا تضيع عند إغلاق التطبيق أو تسجيل الخروج أو العودة بعد عدة أيام**.

مثلًا إذا أضاف المستخدم كلمة:

```text
Operating System
```

فإن النظام يجب أن يحفظ:

* Word ID.
* Word Text.
* Meaning / Translation.
* Word Level.
* Added Date.
* Current State.
* Skill Status.
* Skill Level.
* Last Review.
* Attempts.
* Exposure Count.
* Priority.
* وغيرها من البيانات المطلوبة.

وعندما يعود المستخدم بعد أسبوع، يجب أن يجد النظام حالة الكلمة كما تركها.

# 12. AI لا يتحكم في النظام

هذه قاعدة معمارية مهمة جدًا.

الـ AI يستطيع أن يقول:

```text
User Answer: Correct
Confidence: 0.91
```

ولكنه لا يقرر بنفسه:

> انقل الكلمة إلى Active Vocabulary.

الـ Backend يأخذ نتيجة AI ويطبق Business Rules.

مثلًا:

```text
AI Evaluation
      ↓
Backend Validation
      ↓
WordOS Rules
      ↓
State Update
```

وهذا يمنع أن يصبح النظام معتمدًا بشكل كامل على قرار غير حتمي من نموذج AI.

# 13. Speaking Architecture

Speaking تختلف عن بقية المهارات لأنها تعتمد على تفاعل صوتي.

التدفق الأساسي:

```text
Flutter
   ↓
User Voice
   ↓
Speaking / AI Service
   ↓
AI Conversation
   ↓
Evaluation
   ↓
Python
   ↓
C# Backend
   ↓
Database
```

الـ Backend يحدد:

* مستوى المستخدم.
* الكلمات المستهدفة.
* عدد الكلمات.
* الهدف من الجلسة.
* قواعد المحادثة.

ثم يتم بناء Prompt مناسب.

الـ AI يبدأ المحادثة بشكل طبيعي، لكن لديه تعليمات واضحة حول الكلمات التي يجب أن يناقشها مع المستخدم.

في نهاية المحادثة، يعيد تقييمًا منظمًا، مثل:

```text
Target Word: operating system

Used: Yes
Meaning Correct: Yes
Sentence Understandable: Yes
Pronunciation: Acceptable
Grammar: Minor Errors
Result: PASS
```

والـ Backend هو الذي يستخدم هذه النتيجة لتحديث حالة الكلمة.

# 18. Communication Between C# and Python

التواصل بين Backend وAI Service سيكون باستخدام **RESTful APIs**.

مثلًا:

```text
C# Backend
    |
    | POST /ai/reading
    ↓
Python AI Service
    |
    | AI API
    ↓
AI Provider
    |
    ↓
Python
    |
    ↓
C# Backend
```

يجب أن تكون الـ responses منظمة وقابلة للمعالجة برمجيًا، وليس مجرد نصوص غير منظمة.

مثلًا يمكن أن يرجع AI Service بيانات منطقية مثل:

```json
{
  "result": "success",
  "content": "...",
  "questions": [],
  "target_words": [],
  "evaluations": []
}
```

والشكل النهائي للـ contracts يتم تحديده أثناء implementation.

# 22. Algorithm Validation

يجب أن يكون الـ Analytics جزءًا أساسيًا من المعمارية منذ الـ MVP.

نريد أن نتمكن من الإجابة على أسئلة مثل:

> كم كلمة يضيف المستخدم يوميًا؟

> كم جلسة يكمل؟

> كم إجابة صحيحة في Reading؟

> هل المستخدم ينجح في Listening أكثر أم Writing؟

> كم كلمة تنتقل إلى Active؟

> كم كلمة تفشل في Skill معينة؟

> هل مستوى المستخدم الحالي مناسب فعلًا؟

> هل الخوارزمية تجعل المستخدم ينجح مع الوقت؟

وبالتالي يتم تسجيل البيانات اللازمة لإجراء هذه التحليلات.

# 23. لماذا لا نستخدم Microservices كاملة الآن؟

WordOS مصمم ليكون قابلًا للتوسع، ولكن إدخال عشرات الـ Microservices في الـ MVP سيزيد التعقيد بدون فائدة حقيقية في هذه المرحلة.

لذلك نعتمد:

**Modular Monolith + Separate AI Service**

أي:

```text
Flutter
   ↓
ASP.NET Core Modular Backend
   ↓
PostgreSQL

        ↘
       Python AI Service
```

هذا يعطي المشروع:

* بساطة في التطوير.
* سهولة Debugging.
* سرعة في بناء MVP.
* وضوح في Business Logic.
* فصل AI.
* إمكانية التوسع مستقبلًا.

وفي المستقبل، إذا أصبح أحد أجزاء النظام يحتاج إلى Service مستقل، يمكن فصله دون إعادة بناء النظام بالكامل.

---

# 24. مبدأ قابلية التوسع

يجب ألا يعتمد النظام على AI Provider واحد بشكل مباشر داخل الـ Business Logic.

مثلًا لا نريد:

```text
WordOS Algorithm
      ↓
Specific AI Provider
```

بل:

```text
WordOS Algorithm
      ↓
AI Service Interface
      ↓
AI Provider
```

وبذلك إذا تغير مزود الذكاء الاصطناعي:

```text
Provider A
```

إلى:

```text
Provider B
```

لا يتغير جوهر WordOS.

# 26. مبدأ ملكية القرار

يجب أن يكون واضحًا في جميع أجزاء النظام:

### Flutter

مسؤول عن **Presentation**.

### C# Backend

مسؤول عن **Business Logic + WordOS Algorithm + State Management**.

### Python

مسؤول عن **AI Integration + Prompt Engineering + AI Evaluation Processing**.

### AI Provider

مسؤول عن **Generation / Evaluation according to supplied instructions**.

### PostgreSQL

مسؤولة عن **Persistent Data Storage**.

### Analytics / Logging

مسؤولة عن **Observability and Algorithm Validation**.

# 27. المبدأ الأهم في المعمارية

WordOS يجب ألا يكون:

> AI Application with some vocabulary features.

بل يجب أن يكون:

> **Word Learning Operating System powered by AI.**

فالـ AI هو محرك مساعد لإنشاء المحتوى والتقييم، بينما **WordOS Algorithm هو النظام الذي يقرر رحلة الكلمة**.

بالتالي:

```text
AI ≠ WordOS

AI = Intelligence Layer

WordOS = Learning System
```

وهذا الفصل هو أحد أهم القرارات المعمارية في المشروع.
